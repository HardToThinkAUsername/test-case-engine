# 业务树建模理论 — 优化方向

> 这些优化点不依赖外部因素（需求文档质量、AI 能力等），纯粹是建模理论本身可以改进的方向。

---

## 1. 树模型 → 图模型

**问题**：业务流程不是树，是图。树假设每个分支点之后只有一条路径到叶子节点，但真实业务有循环和回退。

```
支付 → 支付失败 → 重试支付 → 成功
      ↑__________________|
```

树模型把"支付失败 → 重试"拉直成一条独立路径，和"支付成功"并列。但"重试"不是一个独立场景，它是"支付"这个操作的反馈循环。

**优化方向**：在树的基础上叠加**状态机**。入口点之间不是孤立的，它们共享状态（订单状态：待支付 → 已支付 → 已发货），跨入口点的状态流转才是真正的业务逻辑。同级节点之间的关系也应该被建模（并行、互斥、依赖）。

---

## 2. 入口点之间是孤立的

**问题**：当前每个入口点独立建树。但"加入购物车 → 提交订单 → 支付 → 确认收货"是一条链，后面每一步的前提是前面一步成功。孤立建模导致跨入口点的中间状态被忽略——比如"提交订单成功但支付回调丢失"发生在两个入口点之间，不属于任何一个入口点内部的流程。

**优化方向**：增加**入口点之间的连接边**。不只是每个入口点内部有流程，入口点之间也应该有链接关系（前置条件、触发条件、状态变更）。从"入口点森林"变成"业务流程图"。

---

## 3. L3 异常模板是机械匹配

**问题**：10 类模板对所有节点无差别应用。但"并发冲突"对"查看商品列表"有意义吗？"权限拒绝"对"系统自动关闭超时订单"有意义吗？机械匹配产生两个问题：噪音（无关场景被生成）和遗漏（某些节点特有的异常没被模板覆盖）。

**优化方向**：为每个节点类型（用户操作 / 系统事件 / 外部触发）定义**适用的异常模板集**。不同类型的节点有不同的异常倾向，应该按节点类型选择性匹配，而非全部 10 类无差别应用。

---

## 4. L3 和 L4 的边界模糊

**问题**：L3 的"外部依赖失败"和 L4 的"逆向思考"会产生同一个场景——"支付回调丢失"既可以来自模板匹配，也可以来自"如果回调成功但库存扣减失败"的逆向思考。同层级的"并发冲突"和"渐进式假设"也会重叠。

**优化方向**：L3 和 L4 的区分标准应该是"确定性"——L3 是**确定性匹配**（给定节点和模板，场景唯一确定），L4 是**非确定性探索**（同一个技术可以从不同角度产生不同场景）。如果两者产生同一场景，应归到 L3，避免重复计数。

---

## 5. 没有风险权重

**问题**：所有分支点被平等对待。但"支付失败"和"商品排序降序"的测试重要性显然不同。业务树不区分风险等级，导致后续的测试优先级完全依赖人工标注 P1/P2/P3。

**优化方向**：在每个分支点上增加**风险维度**：

| 维度 | 含义 | 评分 |
|------|------|------|
| 影响面 | 影响多少用户 / 涉及多少金额 | 1-5 |
| 发生概率 | 常见操作还是罕见场景 | 1-5 |
| 检测难度 | 是否容易被发现 / 是否有监控 | 1-5 |

后续的用例优先级可以基于风险自动计算（如 影响面 × 发生概率 ÷ 检测难度），而不是靠人工标注。

---

## 6. 缺少跨切条件层

**问题**：有些条件会同时影响多个步骤。比如"用户是 VIP"影响：
- 商品价格（Step 3）
- 运费计算（Step 5）
- 退款政策（Step 8）

在树模型里，这个条件在三个分支点被重复建模三次。应该建模为**跨切条件**，一次定义，多处引用。

**优化方向**：增加"跨切条件"层。模型层级变为：

```
入口点 → 业务流程 → 分支点 → 跨切条件
```

跨切条件定义了"哪些用户属性/系统状态会同时影响多个分支点的行为"，避免重复建模和遗漏。

---

## 7. 输入类型单一

**问题**：当前只支持需求文档作为输入。但业务建模的输入可以更丰富。

| 输入类型 | 示例 | 价值 |
|----------|------|------|
| 需求文档 | PRD、功能说明、用户故事 | 当前已支持 |
| 代码 | 已有代码仓库 | 比需求文档更真实——需求写的是"应该做什么"，代码是"实际在做什么" |
| 历史缺陷 | Bug 数据库、线上事故报告 | 给节点加风险权重，不是猜"可能出问题"，而是"这里出过问题" |
| 增量需求 | 需求变更的 delta | 只更新受影响节点，避免全量重跑 |
| 竞品/领域知识 | 同类产品已知问题模式 | 作为 L4 想象力场景的外部输入 |

**其中代码是最有价值的扩展输入**。大量遗留系统没有需求文档，从代码反向构建业务模型，既可以补文档，又可以做代码评审。

**优化方向**：支持多输入源，不同类型的输入走不同的建模策略（见下方"建模策略选择"）。

---

## 8. 建模策略选择

**问题**：树模型和图形模型各有所长，没有一种模型通吃所有场景。建模类型的选择取决于三个变量：

| 变量 | 需求 → 测试用例 | 代码 → 代码评审 |
|------|:---:|:---:|
| 输入的确定性 | 低（自然语言，模糊） | 高（AST，精确） |
| 需要建模的维度 | 业务流程 + 分支条件 | 控制流 + 调用链 + 状态 + 数据流 |
| 错误代价 | 漏场景（可接受） | 假阳性（不可接受） |

**优化方向**：建立**建模策略选择框架**，根据输入类型和输出目标自动选择建模方式：

| 场景 | 推荐模型 | 原因 |
|------|---------|------|
| 需求文档 → 测试用例 | 树 + 状态机叠加 | 树保下限，状态机提上限 |
| 代码 → 代码评审 | 纯图（控制流图 + 调用图 + 状态机 + 数据流图） | 代码天然是图，用树会丢信息 |
| 需求 + 代码 → 一致性检查 | 需求侧建树，代码侧建图，树投影到图做 diff | 发现"需求说了但代码没做"和"代码做了但需求没写" |
| 历史缺陷 → 风险评估 | 加权图（在已有图上加风险权重） | 真实数据驱动，非猜测 |

---

## 9. 多 Skill 架构

**问题**：当前只有一个 skill（测试用例生成）。但方法论本身是通用的，可以落地到多个场景。

**结论**：**一个仓库，多个 skill，共享方法论，独立入口。**

```
test-case-engine/
├── methodology/                    # 共享方法论（所有 skill 都读）
│   ├── business-tree.md            # 什么是业务树，怎么建
│   ├── business-graph.md           # 什么是业务图，怎么建
│   ├── coverage-layers.md          # L1-L4 分层覆盖
│   └── state-machine.md            # 状态机建模方法
├── skills/
│   ├── test-case-generator/        # 需求 → 测试用例
│   │   ├── SKILL.md
│   │   └── prompts/
│   ├── code-reviewer/              # 代码 → 代码评审
│   │   ├── SKILL.md
│   │   └── prompts/
│   ├── impact-analyzer/            # 需求变更 → 受影响用例
│   │   ├── SKILL.md
│   │   └── prompts/
│   └── requirement-validator/      # 需求 + 代码 → 一致性检查
│       ├── SKILL.md
│       └── prompts/
```

**分拆的原因**：
- 每个 skill 的触发词不同，合并会导致触发词爆炸
- 用户的心智模型是"任务"（帮我生成用例 / 帮我评审代码），不是"方法论"
- 每个 skill 的流程完全不同，合并后 AI 需要自己判断走哪条分支
- 分多个 skill 更容易被社区搜索发现

---

## 总结

| # | 问题 | 本质 | 优化方向 |
|---|------|------|---------|
| 1 | 树不是图 | 模型表达能力不足 | 叠加状态机 |
| 2 | 入口点孤立 | 缺少横向连接 | 增加入口点之间的边 |
| 3 | L3 机械匹配 | 模板没有适用条件 | 按节点类型分类模板 |
| 4 | L3/L4 边界模糊 | 分类标准不清晰 | 确定性 vs 非确定性 |
| 5 | 没有风险权重 | 缺少优先级依据 | 影响面 × 概率 × 检测难度 |
| 6 | 跨切条件重复 | 缺少复用层 | 跨切条件层 |
| 7 | 输入类型单一 | 只支持需求文档 | 支持代码、历史缺陷、增量需求、竞品知识 |
| 8 | 建模策略未区分场景 | 一个模型用到底 | 建模策略选择框架 |
| 9 | 单 Skill 架构 | 方法论和应用耦合 | 多 Skill + 共享方法论 |
