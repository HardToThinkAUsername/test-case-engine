# 测试用例提取指南

## Goal

从需求文档出发，通过业务建模→需求评审→测试大纲→用例生成的完整流程，输出覆盖所有场景的测试用例Excel文档。

## Operating Constraints

- **显式引导**：每项要求必须具体明确
- **完整性**：L1-L3必须100%覆盖
- **先广度再深度**：先覆盖所有场景，再逐个生成用例
- **零冗余**：不得生成重复用例
- **宪法约束**：遵循宪法原则

## Pre-Execution Checks

1. 检查`.test-case/constitution.md`是否存在
2. 加载宪法文件
3. 确认需求文档路径
4. **处理文档格式**（如果不是文本格式）：

**文档格式处理规则**：

| 格式 | 处理方式 |
|------|----------|
| .md / .txt | 直接读取 |
| .docx | 需要转换为文本 |
| .pdf | 需要转换为文本 |
| .doc（旧版Word） | 需要转换为文本 |

**.docx格式处理**：

方式1：建议用户转换（最简单）
```
请将.docx文件另存为.txt或.md格式，然后再提供给我。
```

方式2：使用Python提取文本
```python
# 安装依赖：pip install python-docx
from docx import Document

doc = Document('需求文档.docx')
text = '\n'.join([para.text for para in doc.paragraphs])

# 保存为txt文件
with open('需求文档.txt', 'w', encoding='utf-8') as f:
    f.write(text)
```

方式3：请用户复制粘贴
```
由于.docx是二进制格式，我无法直接读取。
请将需求文档内容复制粘贴到这里，我来帮你分析。
```

**.pdf格式处理**：

方式1：请用户复制粘贴（最简单）
```
请将PDF中的需求文档内容复制粘贴到这里。
```

方式2：使用Python提取文本
```python
# 安装依赖：pip install pdfplumber
import pdfplumber

with pdfplumber.open('需求文档.pdf') as pdf:
    text = '\n'.join([page.extract_text() for page in pdf.pages])

# 保存为txt文件
with open('需求文档.txt', 'w', encoding='utf-8') as f:
    f.write(text)
```

**处理流程**：
1. 识别文档格式
2. 如果是文本格式（.md/.txt）→ 直接读取
3. 如果是非文本格式（.docx/.pdf）→ 转换为.txt → 再读取
4. 转换后保存到 `.test-case/` 目录
5. 继续执行后续步骤

## Execution Steps

### Phase 1: 业务建模

#### Step 1: 解析需求文档

读取需求文档，逐章节提取信息：

**提取规则**：

| 文档章节 | 提取内容 | 提取方式 |
|----------|----------|----------|
| 用户故事 | 用户角色、操作、目标 | 提取"作为xxx，我想xxx，以便xxx" |
| 功能描述 | 具体功能点、操作步骤 | 提取"可以xxx"、"支持xxx"、"能够xxx" |
| 异常处理 | 异常情况、系统响应 | 提取"如果xxx"、"当xxx时"、"失败" |
| 非功能需求 | 性能、并发、安全 | 提取数字指标 |

**逐段扫描**：
1. 从文档开头到结尾，逐段阅读
2. 对每个段落，判断是否包含入口点或业务流程
3. 记录所有发现的信息

输出：结构化需求数据

**验证**：是否遗漏文档章节？是否遗漏用户故事？

---

#### Step 2: 识别业务入口点

根据需求文档，**逐句逐段**识别入口点。不要假设文档是用户故事格式——需求文档可能是功能列表、PRD、会议纪要、或混合格式。

---

##### 2.1 入口点分类体系

入口点分为 4 类：

| 类型 | 定义 | 触发方式 | 示例 |
|------|------|----------|------|
| **用户操作** | 用户主动触发的操作 | 点击、输入、提交、选择、上传、下载 | 提交订单、下载文件、选择设备 |
| **系统事件** | 系统内部事件触发 | 定时/延时/状态变更/条件达成 | 门禁通过后自动创建、超时自动关闭 |
| **外部触发** | 外部系统调用触发 | 回调、webhook、API 调用 | 接收支付回调、接收禅道构建通知 |
| **配置/规则** | 配置或规则驱动的自动化 | 按规则分配、策略匹配 | 按产线分配负责人 |

---

##### 2.2 中文需求文档表述模式库

逐句扫描需求文档，对每句话按以下模式判断：

**明确是入口点的表述**：

| 表述模式 | 入口点类型 | 示例 | 提醒 |
|----------|-----------|------|------|
| "用户可以xxx" | 用户操作 | "用户可以注册" → EP: 用户注册 | |
| "xxx可以yyy" | 用户操作 | "测试管理平台可以关联禅道构建" → EP: 关联禅道构建 | 主语不一定是"用户"，可能是"平台/系统" |
| "一键xxx" | 用户操作 | "一键下载可执行程序" → EP: 下载可执行程序 | "一键"是操作方式的描述，本质是操作 |
| "提交xxx时" | 用户操作 | "提交测试单时可以关联构建" → EP: 关联构建 | 操作时机描述，操作本身是入口点 |
| "xxx下拉选择yyy" | 用户操作 | "任务下拉选择测试设备" → EP: 选择测试设备 | 包含交互控件名称 |
| "当xxx时，系统yyy" | 系统事件 | "当支付超时时自动取消" → EP: 支付超时处理 | 触发条件+系统动作 |
| "xxx后，自动yyy" | 系统事件 | "门禁通过后自动创建测试单" → EP: 自动创建测试单 | 条件触发+自动执行 |
| "xxx通过/完成后，yyy" | 系统事件 | "门禁通过后创建同名测试单" → EP: 创建同名测试单 | 即使没有"自动"二字，也是系统触发 |
| "自动xxx" | 系统事件 | "自动关闭超时订单" → EP: 订单超时关闭 | |
| "接收xxx" | 外部触发 | "接收支付回调" → EP: 支付回调 | |
| "按xxx规则分配/创建" | 配置/规则 | "按产线自动分配负责人" → EP: 负责人分配 | 如果有明确触发条件，归入系统事件 |

**需要判断的歧义表述**：

| 表述模式 | 判断方法 | 示例 |
|----------|----------|------|
| "xxx支持yyy" | **"支持"后面跟的是不是用户可直接触发的动作？** 是 → 入口点；否 → 功能特性 | "支持一键下载" → ✅ 入口点（用户能点击下载按钮）；"支持分页" → ❌ 功能特性（用户不能点击"分页"按钮） |
| "xxx增加/新增yyy" | **"增加"后面跟的是新操作还是新展示？** 操作 → 入口点；展示/字段 → 功能特性 | "增加实时展示成功条数" → ❌ 功能特性（展示数据）；"新增任务下拉选择设备" → ✅ 入口点（用户可以选择） |
| "现在xxx" | 同上，去掉"现在"后按"支持/增加"规则判断 | "现在申请单详情支持一键下载" → ✅ 入口点 |

**明确不是入口点的表述**：

| 表述模式 | 实际类型 | 示例 | 处理方式 |
|----------|----------|------|----------|
| "xxx失败/异常时" | 异常分支 | "支付失败时提示用户" | 不是入口点，是已有入口点的分支走向 |
| "xxx不可用时" | 异常分支 | "禅道不可用时提交不受影响" | 同上 |
| "实时展示xxx" | 界面展示 | "实时展示用例执行成功条数" | 不是入口点，是功能特性。标记为数据展示需求 |
| "合并到一列展示" | 界面布局 | "时间合并到一列展示" | 不是入口点，是界面布局变更 |
| "增加xxx的展示" | 界面展示 | "增加分配时间的展示" | 不是入口点，是新增展示字段 |
| "xxx格式为yyy" | 格式规范 | "时间格式统一为yyyy-MM-dd" | 不是入口点，是展示规范 |
| "按规则xxx"（无触发条件） | 业务规则 | "负责人按产线和业务归属分配" | 是业务规则，需寻找触发条件或标记为缺少入口点 |

---

##### 2.3 入口点判断决策树

对每条需求描述，按以下顺序判断：

```
读到一个功能描述
  │
  ├─ 1. 有明确的操作动词（点击/选择/提交/下载/上传/创建/删除/修改/关联/配置）？
  │   └─ 是 → 用户操作入口点 → 记录
  │
  ├─ 2. 有触发条件 + 自动动作（当xxx时/xxx后/xxx通过后/xxx完成后）？
  │   └─ 是 → 系统事件入口点 → 记录
  │
  ├─ 3. 有外部系统动作（回调/通知/webhook/接收）？
  │   └─ 是 → 外部触发入口点 → 记录
  │
  ├─ 4. 是配置/规则驱动的自动化行为？
  │   └─ 是 → 配置/规则入口点 → 记录，并检查是否有明确的触发条件
  │
  ├─ 5. 描述的是某个操作的失败/异常/不可用情况？
  │   └─ 是 → 不是入口点，是已有入口点的分支 → 标记为分支点，在 Step 4 处理
  │
  └─ 6. 描述的是展示/布局/格式/字段？
      └─ 是 → 不是入口点，是功能特性或展示需求 → 标记为"非入口点"，在业务树中记录为功能特性
```

**注意**：一条需求可能包含多个入口点。例如"驱动平台增加实时展示用例执行的成功条数和失败条数，新增任务下拉选择测试设备可以看到设备状态"包含 0 个入口点（全部是展示需求）和 1 个入口点（下拉选择设备）。

---

##### 2.4 隐含入口点检测

有些入口点不是直接表述的，而是隐含在业务规则中。对每个依赖"外部数据"或"判断条件"的规则，追问：

```
规则："负责人按产线和业务归属自动分配"
  → 追问：产线和业务归属从哪里来？
  → 隐含入口点：从项目配置读取产线和业务归属
  → 如果需求没描述"怎么读配置"，标记为评审问题

规则："选择禅道构建进行关联"
  → 追问：构建列表从哪里来？
  → 隐含入口点：从禅道加载构建列表
  → 这是外部系统调用，标记为外部触发或依赖
```

检查清单：
- [ ] 每个条件判断（if/else）的判定依据有数据来源吗？
- [ ] 每个下拉列表/选择框的数据源有描述吗？
- [ ] 每个"自动分配/自动创建"的输入参数有来源吗？

---

##### 2.5 输出格式

对每个识别到的入口点，记录：

```
入口点ID: EP001
类型: 用户操作
来源: 需求文档第X条
描述: 用户点击"一键全部下载"按钮
触发动作: 点击按钮
输入参数: 申请单ID、下载类型（可执行程序/资源文件）
前置条件: 用户已登录、有下载权限、申请单处于可下载状态
```

输出：入口点列表

**验证**：
- [ ] 是否遗漏入口点？逐条需求复盘
- [ ] 是否把功能特性/展示需求误认为入口点？逐条决策树复盘
- [ ] 是否把异常分支误认为入口点？
- [ ] 每个隐含入口点是否已标记？

---

#### Step 3: 追踪业务流程

对每个入口点追踪完整业务流程：

- 识别所有步骤
- 识别步骤之间的依赖关系
- 追踪到叶子节点（不再有后续步骤）

**验证**：是否追踪到叶子节点？

---

#### Step 4: 识别分支点

识别每个流程节点上的所有分支：

- 条件分支（if/else）
- 异常分支（try/catch）
- 状态分支（不同状态的行为）
- 空分支（必须标记）

**验证**：是否遗漏分支？空分支是否标记？

---

#### Step 5: 构建业务树

合并入口点、流程、分支信息，构建完整业务树。

输出：业务树JSON

---

### Phase 1.5: L4 想象力增强场景生成

在构建业务树后，按优先级应用10种想象力增强技术，为每个入口点生成额外的场景。

**1. 逆向思考**（优先级1）：
```
对业务流程中的每个正常步骤：
  问："如果这步成功但下一步失败会怎样？"
  例：订单创建成功但库存扣减失败 → 钱扣了但没库存
生成对应场景
```

**2. 反模式学习**（优先级2）：
```
识别当前业务所属领域（电商/支付/社交...）
列出该领域常见的bug模式：
  电商：库存超卖、重复支付、退款异常
  支付：掉单、重复扣款、金额不一致
检查当前业务是否也存在这些模式
生成对应场景
```

**3. 渐进式假设**（优先级3）：
```
对关键操作，从简单假设逐步放宽（注意区分功能测试和性能测试）：

功能测试相关：
  正常输入 → 边界值（最小值、最大值、空值）→ 恶意输入
  单条数据 → 多条数据（验证分页、批量处理逻辑）
  正常网络 → 断网（验证离线处理、重试机制）

性能测试相关（单独归类，不混入功能测试）：
  1个用户 → 100个并发用户 → 1000个并发用户
  1条数据 → 10000条数据（验证大数据量处理性能）
  正常网络 → 慢网络（3秒延迟）（验证超时处理性能）

判断标准：如果场景关注"系统能做什么"→功能测试
         如果场景关注"系统能做多快/多好"→性能测试
对每个变化生成场景，但要标记测试类型
```

**4. 多角色视角**（优先级4）：
```
从以下角色分别思考：
  普通用户：会怎么误操作？（点错按钮、重复点击、中途放弃）
  攻击者：会怎么恶意利用？（注入、越权、重放攻击）
  运维人员：系统出问题时怎么恢复？（数据不一致、服务中断）
  外部系统：调用会怎么出错？（超时、格式错误、签名失败）
对每个角色生成场景
```

**5. 数据全生命周期**（优先级5）：
```
对业务中的每个数据实体（用户、商品、订单、支付记录）：
  创建：创建时缺少校验？唯一性约束？
  存储：存储空间不足？存储失败？
  读取：数据不存在？数据被篡改？数据过期？
  更新：并发更新冲突？部分更新失败？
  删除：删除后仍被引用？误删恢复？
对每个阶段生成场景
```

**6. 逐层追问**（优先级6）：
```
对每个已识别的场景：
  第1层：这个场景发生后会怎样？
  第2层：然后呢？导致什么后果？
  第3层：这个后果会影响其他功能吗？
  第4层：最坏情况下会怎样？
挖掘更深层的影响链
```

**7. 类比推理**（优先级7）：
```
思考类似业务系统（淘宝/京东/美团...）通常会遇到的问题
回忆这些问题的根因
检查当前业务是否也存在类似的风险
生成对应场景
```

**8. 组合交叉**（优先级8）：
```
列出业务中的关键条件：
  用户状态：未登录/已登录/已锁定
  订单状态：待支付/已支付/已发货/已完成/已取消
  库存状态：充足/不足/为0
将条件两两组合，检查每种组合的处理
生成对应场景
```

**9. 时间和顺序**（优先级9）：
```
对操作序列分析：
  先A后B vs 先B后A：结果是否不同？
  同一操作执行两次：是否幂等？
  操作执行到一半中断：恢复后状态一致吗？
  操作之间间隔1秒 vs 1小时：结果不同吗？
对每个时序问题生成场景
```

**10. 规模和压力**（优先级10）：
```
对关键操作分析不同规模（注意区分功能测试和性能测试）：

功能测试相关：
  数据量：1条 vs 10条（验证分页逻辑、批量处理逻辑）
  文件大小：1KB vs 1MB（验证文件上传功能，除非需求明确要求支持大文件）
  数据状态：正常数据 vs 损坏数据 vs 格式错误数据

性能测试相关（单独归类，不混入功能测试）：
  数据量：100条 vs 10000条（验证大数据量处理性能）
  用户量：100人并发 vs 10000人并发（验证并发处理性能）
  文件大小：10MB vs 100MB（验证大文件处理性能）

判断标准：如果场景关注"功能是否正确"→功能测试
         如果场景关注"性能是否达标"→性能测试
对每个规模变化生成场景，但要标记测试类型
```

### Phase 2: 需求评审

#### Step 6: 基于业务树评审需求

对业务树的每个分支进行评审：

**评审维度（逐维度检查）**：

| 维度 | 检查项 | 检查方法 |
|------|--------|----------|
| 完整性 | 是否有遗漏的业务分支？ | 对比业务树与需求文档，检查是否有未覆盖的功能 |
| 一致性 | 需求之间是否有矛盾？ | 检查不同章节的描述是否冲突 |
| 清晰性 | 是否有模糊的描述？ | 检查是否有"等"、"等等"、"适当"等模糊词 |
| 边界性 | 是否有未定义的边界条件？ | 对每个参数检查边界值是否定义 |
| 异常性 | 是否有未描述的异常处理？ | 对每个操作检查失败时的处理 |

**输出格式**：

```json
{
  "review_result": {
    "status": "pending",
    "issues": [
      {
        "id": "ISSUE001",
        "dimension": "完整性",
        "description": "需求未定义用户注销功能",
        "severity": "高",
        "suggestion": "建议增加用户注销功能的需求描述"
      }
    ],
    "summary": {
      "total_issues": 5,
      "by_dimension": {
        "completeness": 2,
        "consistency": 0,
        "clarity": 1,
        "boundary": 1,
        "exception": 1
      }
    }
  }
}
```

#### Step 7: 用户调整与再评审

**交互协议**：

1. **输出评审结果**：展示所有发现的问题
2. **等待用户反馈**：用户语言描述如何调整
3. **理解调整意图**：智能体解析用户的自然语言描述
4. **更新业务树**：根据调整意图更新业务树
5. **再次评审**：对更新后的业务树重新评审
6. **循环**：直到用户确认评审通过

**用户调整的输入格式**（自然语言）：

```
用户可能说：
- "注销功能不需要"
- "密码错误5次后锁定时间改为1小时"
- "增加批量删除购物车的功能"
- "支付超时时间改为15分钟"
```

**智能体处理调整的步骤**：

```
1. 解析用户意图：用户想增加/删除/修改什么？
2. 定位业务树节点：这个调整影响业务树的哪个分支？
3. 更新业务树：修改对应的节点
4. 标记调整历史：记录这次调整的内容和原因
```

**终止条件**：

- 用户明确表示"可以了"或"通过"
- 所有发现的问题都已处理（确认或拒绝）

---

#### Step 7: 用户调整与再评审

用户语言描述需求调整：
- 智能体理解调整意图
- 更新业务树
- 再次评审
- 循环直到用户满意

### Phase 3: 测试大纲

#### Step 8: 构建测试大纲

基于确认后的业务树，构建测试大纲：

```
测试大纲
├── 模块A
│   ├── 测试点A1（L1主路径）
│   ├── 测试点A2（L2分支路径）
│   ├── 测试点A3（L3异常）
│   └── 测试点A4（L4想象力场景）
├── 模块B
│   └── ...
```

每个测试点标注：
- 来源层级（L1/L2/L3/L4）
- 优先级（P1/P2/P3）
- 测试重点

---

### Phase 4: 用例生成

#### Step 9: 逐个场景生成用例

根据测试大纲和业务树，对每个测试点生成测试用例：

**用例生成规则**：

| 来源 | 用例类型 | 优先级 | 测试类型 |
|------|----------|--------|----------|
| L1 主路径 | 正向用例 | P1 | 功能测试 |
| L2 分支路径 | 分支用例 | P1-P2 | 功能测试 |
| L3 异常模板 | 异常用例 | P2 | 功能测试 |
| L4 想象力场景 | 边界/组合用例 | P2-P3 | 功能测试或性能测试（根据场景判断） |

**测试类型判断标准**：

| 场景特征 | 测试类型 | 示例 |
|----------|----------|------|
| 业务逻辑、流程、规则 | 功能测试 | 正常下单、库存校验、状态流转 |
| 并发用户数、响应时间 | 性能测试 | 1000并发用户、响应时间<3秒 |
| 大数据量处理逻辑 | 功能测试 | 分页显示10000条数据 |
| 大数据量处理性能 | 性能测试 | 10000条数据查询时间 |
| 文件上传功能 | 功能测试 | 上传1MB文件 |
| 文件上传性能 | 性能测试 | 上传100MB文件 |

**每个用例必须包含**：

```json
{
  "id": "TC001",
  "title": "正常下单支付成功",
  "priority": "P1",
  "type": "positive",
  "test_type": "functional",
  "module": "订单管理",
  "source": "L1主路径 | 入口点EP001",
  "preconditions": ["用户已登录", "商品存在", "库存充足"],
  "steps": [
    "1. 选择商品",
    "2. 点击提交订单",
    "3. 确认支付",
    "4. 完成支付"
  ],
  "expected_result": "订单创建成功，状态变为已支付",
  "related_requirement": "需求文档第X条"
}
```

**广度追问**：生成后追问"还有其他场景吗？"

---

#### Step 10: 去重与验证

**去重检查**：
- 检查是否有重复用例（标题或步骤高度相似）
- 检查是否所有测试点都有用例

**Schema 校验**：

生成完成后，必须用 `schemas/test-cases.schema.json` 校验输出。校验规则：

1. 所有必填字段必须存在：id, title, priority, type, test_type, module, source, preconditions, steps, expected_result, related_requirement
2. `id` 格式：`TC-{模块}{功能}-{三位序号}`，如 `TC-M1F1-001`
3. `priority` 只能是 P1/P2/P3
4. `type` 只能是 positive/branch/exception/boundary
5. `test_type` 只能是 functional/performance
6. `preconditions` 和 `steps` 不能为空数组
7. coverage_report 中 L1-L3 的覆盖率必须为 100%

**验证失败** → 补充遗漏/合并重复/修正格式 → 重新验证
